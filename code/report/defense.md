### Q002：Lab2 总体上要解决什么问题？

**答案：** 让内核知道哪些物理内存可以使用，并能按页申请和归还连续内存。启动映射使 CPU 能访问内存；页初始化建立管理记录并区分占用区和可用区；分配器再处理选块、拆分、释放和合并。这几部分共同提供后续内核功能的物理内存基础。

### Q003：从固件进入内核到分配器自检，完整调用链是什么？

**答案：** 主要顺序为：

```text
固件交出控制权及启动参数
→ kern_entry 保存参数、准备 satp
→ 开启 Sv39，依靠身份映射衔接低地址取指
→ 设置高地址栈并跳到 kern_init
→ 清理 BSS、解析 DTB、初始化控制台
→ pmm_init 选择并初始化管理器
→ page_init 建立管理记录并计算可用区
→ init_memmap 登记初始空闲块
→ check_alloc_page 调用当前管理器自检
→ SLUB 分支继续执行 slub_init、slub_check
→ 输出信息并进入空转
```

源码入口见 [entry.S](../kern/init/entry.S)、[init.c](../kern/init/init.c)、[pmm.c](../kern/mm/pmm.c)。

## 二、地址、页与硬件基础

### Q009：物理地址与虚拟地址分别是什么？

**答案：** 物理地址用于定位物理地址空间中的位置，本实验主要讨论其中的 RAM；虚拟地址是程序在开启地址转换后使用的地址，需要根据页表转换到物理位置。不同虚拟地址可以映射到同一物理地址。一个很大的虚拟地址数值不代表机器安装了同样大的 RAM。

### Q010：MMU、操作系统和页表分别做什么？

**答案：** 操作系统准备页表及映射规则，页表存放在内存中，MMU（Memory Management Unit，内存管理单元）是 CPU 中执行地址转换的硬件。取指和访存时，硬件按当前地址转换模式查询规则，并可复用已有转换缓存；软件也可以为了构造、检查映射而读取页表。

### Q011：PC 是什么，开启分页为什么会影响取指？

**答案：** PC 保存执行指令时使用的地址。开启分页后，取指地址需要经过虚实转换；写入 `satp` 不会自动把 PC 数值替换成对应高地址。因此同一个低地址数值，在转换模式改变后也需要有效映射才能继续访问指令。

### Q012：页、物理页框和页内偏移是什么？

**答案：** 页是按固定大小划分的地址区间，物理页框是物理内存中对应大小的区域。本分配器按 4 KiB 管理物理页。页内偏移说明要访问这一页里的第几个字节，4 KiB 有 4096 个字节，需要 12 位表示偏移。

### Q013：索引到底是什么，谁使用索引？

**答案：** 索引是数组中元素的编号。例如有 512 项的页表，其编号是 0～511。MMU 从虚拟地址中取出索引，选择页表项；内核填表时也要计算这些编号。`pages[i]` 的 i 则是软件管理数组的索引，表示从 RAM 起点数的第 i 个页，两种索引服务于不同结构。

### Q014：页表项、叶表项与下一级页表有什么区别？

**答案：** 页表项简称 PTE（Page Table Entry）。有效项可以给出下一级页表的位置，让硬件继续查询；也可以作为叶项，直接给出目标物理区间和访问权限。Sv39 中，R 或 X 为 1 表示叶项，R/W/X 全为 0 的有效项可指向下一级；W 为 1 而 R 为 0 属于非法组合。当前启动表使用同时带 R/W/X 权限的叶项，在根表处结束查询。

### Q015：页表自己存在哪里，硬件怎样先找到它？

**答案：** 页表本身占用真实的物理内存。`satp` 保存根页表的物理页号，硬件据此找到第一张表，再执行转换。当前启动根表属于内核静态布局，其所在物理页被保留，不会交给分配器使用。

### Q016：为什么使用高地址映射，跳过去会搬运内核吗？

**答案：** 高地址映射让内核按约定的虚拟地址布局运行，同时将这些地址映射到实际装载位置。跳转只改变后续使用的指令地址，不会复制或搬运整份内核。当前实验的高地址映射也不等于已经实现完整进程隔离。

### Q017：分配物理页、建立虚拟映射和 malloc 是同一件事吗？

**答案：** 物理页分配器选择并登记可用页；页表管理负责建立虚拟地址到物理地址的对应；`malloc` 一类堆分配接口通常按字节或对象提供空间。这些层可以配合，但当前 `alloc_pages()` 主要修改页管理信息，不自动完成另外两层的全部工作。

## 三、Sv39、页表与 satp

### Q018：Sv39 的地址结构是什么，64 位高地址为什么有效？

**答案：** Sv39 是 RISC-V 的一种监管者虚拟内存转换模式，名称中的 39 表示参与地址结构的位数：三个 9 位虚拟页号索引 VPN[2]、VPN[1]、VPN[0]，再加 12 位页内偏移。有效地址的第 63～39 位必须与第 38 位相同，高位区间通过符号扩展形成；并非所有任意 64 位数值都是有效 Sv39 地址。

### Q019：为什么地址要分成 9＋9＋9＋12 位？

**答案：** 普通页是 4096 字节，低 12 位表示页内位置。每级页表有 512 项，选择一项需要 9 位，三级索引共 27 位，与偏移相加为 39 位。大页叶项会提前结束查询，低位中的相应部分直接用于区间内定位。

### Q020：为什么一张页表恰好占 4 KiB？

**答案：** 当前每个 PTE 占 8 字节，每张表有 512 项，所以 `512 × 8 = 4096` 字节。表按 4 KiB 对齐，以便通过物理页号表示它的位置。

### Q021：Sv39 支持三级，为什么启动代码只有一张表？

**答案：** Sv39 允许在上层使用大页叶项。当前根表的叶项直接映射 1 GiB，硬件不再访问第二、第三张表。目标物理基址要满足相应大页对齐，当前 `0x80000000` 满足 1 GiB 对齐。

### Q022：satp 有哪些字段，当前怎样设置？

**答案：** `satp` 是监管者地址转换与保护寄存器（Supervisor Address Translation and Protection），决定当前监管者地址转换模式及根表位置。RV64 下的布局为：

| 位范围 | 字段 | 当前设置 |
| --- | --- | --- |
| 63～60 | MODE，转换模式 | 8，表示 Sv39 |
| 59～44 | ASID，地址空间标识 | 0 |
| 43～0 | PPN，根表物理页号 | 当前构建为 `0x80205` |

ASID 可用于区分地址空间，配合转换缓存管理；当前实验没有展开多地址空间管理。MODE 为 0 是 Bare 模式，当前启动从它切换到 Sv39。

### Q023：satp 为什么不能直接填页表的虚拟地址？

**答案：** 硬件首先要定位根表，之后才能利用页表做虚拟地址转换，因此根表位置以物理页号提供。若把高位虚拟地址当成物理位置使用，就不能正确定位实际根表。

### Q024：代码怎样把启动根表虚拟地址变成物理地址？

**答案：** 当前启动映射具有固定偏移 `0xffffffff40000000`，从根表虚拟地址减去它即可得到物理位置。已有构建为：

```text
0xffffffffc0205000 - 0xffffffff40000000 = 0x80205000
```

这是数值计算，成立前提是采用当前约定的线性映射关系。

### Q025：为什么取页号右移 12 位，构造 PTE 却左移 10 位？

**答案：** 物理地址低 12 位是页内偏移，右移后得到页号。PTE 中的 PPN 字段从第 10 位开始，编码到 PTE 时左移 10。`satp` 的根页号字段有自己的布局，不能把 PTE 的编码方式直接套过去。

### Q026：当前 satp 的数值怎样算出来？

**答案：** 依据当前根表物理位置：

```text
根表物理地址 = 0x80205000
根表物理页号 = 0x80205000 >> 12 = 0x80205
satp = (8 << 60) | 0x80205 = 0x8000000000080205
```

这里 `0x80205` 指出表存在哪里。它与叶项中的目标页号 `0x80000` 含义不同，后者指出被映射物理区间从哪里开始。

### Q027：叶项中的 0xcf 表示什么？

**答案：** 它设置 V、R、W、X、A、D 位，表示有效、可读、可写、可执行，并预置访问和写入状态；U、G 位为零。当前叶项值为 `(0x80000 << 10) | 0xcf = 0x200000cf`。A/D 是预先设置的初值，不能据此声称已经观察到实际访问或写入。

### Q028：索引 2 和 511 的表项数值相同，为什么映射不同虚拟地址？

**答案：** 虚拟区间由该项在表中的位置决定，表项内容则给出目标物理基址与权限。两个位置都写同样内容，就能让低位区间和高位区间映射到同一段物理内存。

### Q029：TLB 与 sfence.vma 分别是什么？

**答案：** TLB 等地址转换缓存保存已经得到的翻译结果，减少反复查表。`sfence.vma` 用于同步页表相关的转换状态，避免继续采用不适用的缓存结果。它不创建缺失表项，也不替代显式跳转；写 `satp` 本身也不应被当成自动完成所有翻译缓存同步。

## 四、启动修复与故障定位

### Q030：物理入口 0x80200000 与链接地址 0xffffffffc0200000 如何对应？

**答案：** 固件将执行权交给装在物理内存中的内核入口，链接器则按高位内核地址组织符号。两者相差当前虚实偏移。启动汇编先准备映射，再跳到这些链接符号对应的高地址运行。

### Q031：a0、a1 保存什么，为什么入口要先保存它们？

**答案：** 当前交接约定中，a0 是 hart ID，即硬件线程标识，a1 是 DTB（Device Tree Blob，设备树二进制数据）的物理地址。入口将它们保存到 `boot_hartid`、`boot_dtb`，供后续 C 代码使用。设备树描述内存等硬件信息。这些变量位于 `.data`；`kern_init()` 清理 BSS 时不会把这份已保存的 `.data` 参数一起清掉。

### Q032：身份映射和高地址映射分别是什么？

**答案：** 身份映射让虚拟地址与物理地址数值相同，例如 `0x80200038 → 0x80200038`；高地址映射把高位虚拟地址指向实际低位物理位置，例如 `0xffffffffc0200038 → 0x80200038`。两种访问方式可以同时指向同一份代码。

### Q033：根表索引 2 和 511 怎样计算？

**答案：** 使用 `(va >> 30) & 0x1ff`。对低地址 `0x80200038` 得到 2，对高地址 `0xffffffffc0200038` 得到 511。前者所在区间从 `0x80000000` 开始，后者所在区间从 `0xffffffffc0000000` 开始；内核入口位于各自区间内偏移 `0x200000` 的位置，上述下一条指令则在偏移 `0x200038` 处。

### Q034：汇编里的 .zero 和 .quad 怎样组成根表？

**答案：** 它们是生成数据的汇编指令。`.zero 8 * 2` 填零索引 0、1，接着的 `.quad` 填索引 2；`.zero 8 * 508` 填索引 3～510，最后一条 `.quad` 填索引 511。总数 `2 + 1 + 508 + 1 = 512`，表大小保持 4 KiB。

### Q035：为什么写 satp 后，下一条指令会取不到？

**答案：** 写入之后下一条指令的 PC 仍然是数值 `0x80200038`，但它开始需要地址转换。原始根表只有索引 511 的高地址叶项，低地址使用的索引 2 无效，无法给这次取指提供映射。代码字节仍在物理内存里，失败点在访问规则的衔接。

### Q036：GDB 提供了哪些证据，能排除什么误解？

**答案：** [日志](logs/boot-debug-gdb.log)记录：写前 PC=`0x80200034`、satp=0；单步写入后 PC=`0x80200038`、satp=`0x8000000000080205`，读取该低地址报无法访问。结合页表缺项可以定位过渡映射问题，不能简单解释成内核镜像未装入或编译失败。

### Q037：为什么选择补索引 2，而不是随便增加一条映射？

**答案：** 实际继续执行的低地址提取出的根索引就是 2，补在其他位置不能覆盖这次取指。给索引 2 写入同一物理区间的叶项，是针对已观察故障的局部修复；索引 511 继续支持后面的高地址执行。

### Q038：修好身份映射后，怎样真正进入高地址？

**答案：** 入口继续执行 `sfence.vma`，设置高地址栈指针，再用 `lui`、`addi` 构造 `kern_init` 的高地址，执行 `jr t0` 跳过去。PC 数值是在显式跳转时改变的，后续取指由索引 511 映射到内核物理位置。

### Q039：高地址运行后，身份映射是否被撤销？

**答案：** 没有，当前代码保留索引 2。此次任务修复启动过渡，没有额外实现动态重建启动页表或撤销低地址映射。

### Q040：根表映射了 1 GiB，是否说明有 1 GiB RAM 可分配？

**答案：** 不是。映射范围与实际安装的内存范围分别确定，DTB 才提供实际 RAM 大小。`page_init()` 只管理报告范围内的完整页，并检查其不超出启动映射能力；不能因为地址有映射就把并不存在的 RAM 交给分配器。

## 五、物理页初始化

### Q041：page_init() 的输入、处理和结果分别是什么？

**答案：** 输入来自 DTB 的内存范围、链接器的 `end` 和已有映射布局。处理包括计算页数、布置描述符数组、初始化状态和划定可用区。结果是受管 RAM 中的完整页都有管理记录，已占用页继续保留，明确可用的区间已登记进当前分配器。

### Q042：为什么不直接用 PHYSICAL_MEMORY_END 定义的常量？

**答案：** 常量反映默认布局，实际 RAM 配置可能不同。代码用 DTB 的起点加大小计算结束边界，因此能随 64 MiB、128 MiB 等配置变化。仅依赖固定 `0x88000000` 会把非默认配置处理错。

### Q043：DTB 从哪里来，page_init() 会重新探测所有内存吗？

**答案：** 固件通过 a1 交接设备树地址，`kern_init()` 先调用 `dtb_init()` 解析。随后两个 getter 返回已经解析的范围；`page_init()` 不需要逐页读写来探测 RAM。相关接口见 [dtb.h](../kern/driver/dtb.h)。

### Q044：mem_base、mem_size 和 mem_end 有什么区别？

**答案：** 分别是物理起点、字节大小和不包含在区间内的结束边界。默认值为 `0x80000000`、`0x08000000`、`0x88000000`。区间 `[begin, end)` 的大小用 `end - begin`，不加 1；最后一个有效字节是 `end - 1`。

### Q045：nbase、npage 和 page_count 怎样计算？

**答案：** 三者分别是起始物理页号、结束边界对应的页号上界和实际完整页数：

```text
nbase = 0x80000000 >> 12 = 0x80000
npage = 0x88000000 >> 12 = 0x88000
page_count = npage - nbase = 0x8000 = 32768
```

页号从物理地址零开始编号，管理数组则从这段 RAM 的第一个页开始。

### Q046：骨架注释说 npage 是页数量，为什么答辩要说页号上界？

**答案：** 应以当前转换函数和初始化实际用途为准。`pa2page()` 用物理页号与 npage 比较上界，再减去 nbase 作为数组索引。若将 npage 当作本段 RAM 的页数，就会忽略这段 RAM 从非零物理地址开始的事实；这里的原注释不够准确。

### Q047：PPN(pa) 与 pages[] 索引为什么不一样？

**答案：** `PPN(pa) = pa >> 12` 是从地址零编号的物理页号。`pages[]` 只为当前 RAM 区域建立记录，因此索引为 `PPN(pa) - nbase`。例如物理页号 `0x80000` 对应 `pages[0]`，不是 `pages[0x80000]`。

### Q048：struct Page 有哪些字段，为什么占 40 字节？

**答案：** 包含引用计数 `ref`、状态位 `flags`、空闲块长度 `property` 和链表节点 `page_link`。当前布局为 4 字节 ref、4 字节对齐空隙、8 字节 flags、4 字节 property、4 字节空隙和 16 字节双指针节点，共 40 字节。大小应以当前 ABI 的 `sizeof` 为准。

### Q049：pages[0] 描述的页与它自己存放的位置相同吗？

**答案：** 不相同。它描述从 `0x80000000` 开始的物理页，但这条记录自己存放在管理数组起点，当前物理位置为 `0x80207000`。记录相当于保存状态的信息，数据页和状态记录分别占用内存。

### Q050：为什么初始化管理数组不调用 malloc？

**答案：** 正在建立提供内存的基础设施，不能先假定它已经可用。代码直接选择内核结束之后、已有启动映射覆盖的 RAM 存放记录，计算所需空间并显式保留，再逐项写入。无需依靠已经运行的堆分配器。

### Q051：extern char end[] 声明的到底是什么？

**答案：** 它引用链接脚本在内核各部分之后定义的地址符号，表示内核占用空间的结束边界。声明本身没有新建一个数组，也不是读取某处保存的数值；这里使用的是符号地址。定义见 [kernel.ld](../tools/kernel.ld)。

### Q052：页对齐怎样计算，为什么上取整和下取整都需要？

**答案：** 页边界是 4096 的整数倍。`ROUNDUP` 取不小于原地址的最近页边界，`ROUNDDOWN` 取不大于原地址的最近页边界。当前 `end = 0xffffffffc0206078`，上取整为 `0xffffffffc0207000`；已经对齐的地址保持不变。

### Q053：给 pages 指针赋值之后，管理记录就全部生成了吗？

**答案：** 赋值只选定访问位置，并把它按 `struct Page *` 使用。随后循环才真正写入每条记录的 flags、property、ref 和链表节点。CPU 实际通过高地址写入时，仍由已建立的页表完成地址转换。

### Q054：默认管理数组需要多大空间？

**答案：** `32768 × 40 = 1310720 = 0x140000` 字节，即 1.25 MiB、320 个 4 KiB 页。从 `0x80207000` 开始，因此末尾为 `0x80347000`。这段空间是管理成本，需要从可分配 RAM 中扣除。

### Q055：free_begin 和 free_end 为什么分别这样算？

**答案：** 起点是管理数组物理末尾向上按页对齐，避免把数组还占着的一部分页交出去；终点是实际内存结束边界向下对齐，只开放完整存在的页：

```text
free_begin = ROUNDUP(pages_pa + page_count * sizeof(struct Page), PGSIZE)
free_end = ROUNDDOWN(mem_end, PGSIZE)
```

### Q056：为什么先将所有页标为保留，再开放空闲区？

**答案：** 这样只有明确确认可用的区间进入分配器。固件、内核、静态栈、启动页表和管理数组继续保留，减少遗漏某段占用区而被错误分配的可能。开放由随后的 `init_memmap()` 对合法可用范围执行。

### Q057：PG_reserved 定义成 0，为什么设置后 flags 是 1？

**答案：** 0 表示使用第 0 位，而不是设置值为零。宏执行 `flags |= 1UL << 0`，把该位置 1，所以原先 flags 为零时结果为 1。`PG_property = 1` 使用第 1 位，设置后的对应掩码为 2。

### Q058：ref 为零是否表示空闲，申请后会自动加一吗？

**答案：** 引用计数与空闲结构不是同一项状态。当前分配器不在申请时自动增加 ref，原始检查也要求申请结果的 ref 初值为零。它不能单独用于判断是否可分配；引用关系由实际使用这一页的相应层维护。

### Q059：每页执行 list_init()，是否把全部物理页加入了空闲链表？

**答案：** 没有。它只是让这个节点的前后指针指向自己，准备好初始状态。真正加入全局空闲链表由登记函数执行，而且只将每个空闲块的起始页连接进去。

### Q060：init_memmap() 的两个参数怎样得到？

**答案：** 第一个是可用区首个物理页对应的记录，第二个是完整页数。默认构建中：

```text
pa2page(0x80347000)
= &pages[0x80347 - 0x80000]
= &pages[839]

(0x88000000 - 0x80347000) / 4096 = 31929
```

因此登记从 `pages[839]` 开始的 31929 页。

### Q061：那些 assert 各自检查什么，数组容量为什么先用除法？

**答案：** 检查固定 RAM 起点、正且不超过映射能力的大小、有效页号范围、数组起点位于 RAM、空间容纳全部记录，以及最后确有可用页。容量条件比较“需要几条记录”与“剩余字节数除以每条大小”，避免在检查之前就依赖可能溢出的总大小乘法。

### Q062：内存末尾不对齐，或者不足以容纳数组和空闲页，会怎样？

**答案：** 末尾不足一整页的部分不开放，结束边界向下对齐。若无法放下管理数组或没有剩余完整可用页，当前断言会停止内核，而不是继续建立错误的分配结构。它也没有在失败后自动扩展映射或重新寻找另一段 RAM。

## 六、地址转换与现场计算

### Q063：PADDR、pa2page、page2pa 分别转换什么？

**答案：** 它们的输入、输出属于不同类型：

| 操作 | 输入 | 输出 | 本实验中的作用 |
| --- | --- | --- | --- |
| `PADDR(kva)` | 内核直接映射区的虚拟地址 | 物理地址 | 用固定偏移还原数组等对象的物理位置 |
| `pa2page(pa)` | 被管理范围内的物理地址 | 对应的 `struct Page *` | 找到描述该物理页的管理记录 |
| `page2pa(page)` | 页管理记录指针 | 所描述物理页的起始物理地址 | 从记录定位实际物理页 |

`struct Page *` 指向管理数组，不是该物理页数据区的指针。也不能对任意虚拟地址都套用固定偏移转换；它依赖本实验已经建立的直接映射。定义见 [pmm.h](../kern/mm/pmm.h)。

### Q064：pa2page 和 page2pa 的公式怎样推导？

**答案：** 物理地址右移 12 位得到物理页号，减去 RAM 首个物理页号 `nbase`，得到数组下标；反向操作则先加回 `nbase`，再左移 12 位：

```text
数组下标 i = (pa >> 12) - nbase
pa2page(pa) = &pages[i]
page2pa(&pages[i]) = (i + nbase) << 12

pa = 0x80347000
i = 0x80347 - 0x80000 = 839
page2pa(&pages[839]) = 0x80347000
```

非页对齐的 `pa` 也会落入所在页的记录；反向转换返回页首地址，原来的页内偏移不会保留。使用者必须保证地址属于实际管理范围，不能把这些辅助函数当作完整的非法输入检查器。

### Q065：为什么 Page 指针加一只移动 40 字节，却代表下一张 4096 字节的物理页？

**答案：** C 指针运算按所指类型大小移动。`pages + 1` 指向数组中的下一条记录，记录间距是 `sizeof(struct Page)`，当前为 40 字节；相邻记录描述的物理页相差 4096 字节。

```text
管理记录的地址差：&pages[i + 1] - &pages[i] = 1 条记录
管理记录的字节差：sizeof(struct Page) = 40
描述的物理地址差：page2pa(&pages[i + 1]) - page2pa(&pages[i]) = 4096
```

分配器中的 `base + n` 正是利用记录与物理页一一对应的关系。需要按单字节移动时，应先转换为字符指针。

### Q066：默认 128 MiB 内存怎样分成固件、内核、管理数组和空闲区？

**答案：** 以下数值对应已有个人分支构建日志，区间采用左闭右开写法：

| 区域 | 物理范围 | 页数 |
| --- | --- | --- |
| RAM 起点到内核入口之前的保留区 | `[0x80000000, 0x80200000)` | 512 |
| 内核及其末尾对齐占用 | `[0x80200000, 0x80207000)` | 7 |
| `struct Page` 数组 | `[0x80207000, 0x80347000)` | 320 |
| 初始可分配区 | `[0x80347000, 0x88000000)` | 31929 |
| 合计 | `[0x80000000, 0x88000000)` | 32768 |

前 512 页整体保留给启动环境等用途，并不表示固件恰好用了每个字节。保留页合计 `512 + 7 + 320 = 839`，所以 `32768 - 839 = 31929`。

### Q067：把 QEMU 改成 64 MiB 后，各项数值应该怎样变化？

**答案：** RAM 起点仍为 `0x80000000`，大小变成 `0x04000000`，结束边界变为 `0x84000000`。以同一内核构建为例：

```text
npage       = 0x84000000 >> 12 = 0x84000
page_count  = 0x84000 - 0x80000 = 16384
数组字节数  = 16384 × 40 = 655360 = 0xA0000
数组占用页  = 160
数组起点    = 0x80207000
free_begin  = 0x80207000 + 0xA0000 = 0x802A7000
free_end    = 0x84000000
空闲页数    = (free_end - free_begin) / 4096 = 15705
```

这些结果与 [64 MiB 日志](logs/hews-qemu-64m.log) 对应。

### Q068：64 MiB 是 128 MiB 的一半，空闲页数为什么不是原来的一半？

**答案：** 固件前置保留区和同一内核镜像的占用没有减半，而每页一条的管理数组随总页数减半。因此：

```text
128 MiB：32768 - 512 - 7 - 320 = 31929
 64 MiB：16384 - 512 - 7 - 160 = 15705
```

“总内存减半”不等于“所有开销一起减半”。这也说明应按当前内存范围重新计算数组和空闲区。

### Q069：内核增加几个函数后，原来算好的空闲起点还成立吗？

**答案：** 不一定。链接后的内核结束地址 `end` 可能变化；当它跨过页边界时，数组起点随之移动，空闲起点也会变化。正确实现从链接符号、`sizeof(struct Page)` 和 DTB 重新推导。文档中的具体地址用于解释已有构建，不能替代运行时计算，也不能写成固定答案放进实现。

### Q070：现场没有记住地址时，如何一步步推导可分配区？

**答案：** 先确定“实际 RAM”和“已经占用到哪里”，再计算元数据开销：

```text
mem_end = DTB 中的内存起点 + 大小
page_count = (mem_end >> 12) - nbase
pages_va = ROUNDUP(end, 4096)
pages_pa = PADDR(pages_va)
metadata_end = pages_pa + page_count × sizeof(struct Page)
free_begin = ROUNDUP(metadata_end, 4096)
free_end = ROUNDDOWN(mem_end, 4096)
free_pages = (free_end - free_begin) / 4096
```

先检查数组和可用区确实放得下，再登记。管理数组可以描述自己占用的物理页：记录和被描述对象是两种东西，只要这些页始终保留，就不会把管理数组再次分配出去。

## 七、链表与管理器接口

### Q071：为什么用空闲块链表，而不是每次遍历全部 Page？

**答案：** 相邻空闲页可以组成一个连续块，只需保存“起始页和长度”。例如一段 100 页的空闲区，用一个链表节点和长度 100 就能表示。分配时遍历空闲块即可，不必逐页扫描所有管理记录。每张物理页仍有自己的记录，但只有每个空闲块的起始页进入 `free_list`。

### Q072：什么是双向循环链表，free_list 本身也是一张物理页吗？

**答案：** 每个节点有前驱 `prev` 和后继 `next`；首尾通过哨兵头节点连接成环。`free_list` 是独立的链表头，不是 `struct Page`，也不代表可分配内存。空表时头节点的两个指针都指回自身。

```text
空表：head.next = head，head.prev = head
非空：head ↔ 块 A 的节点 ↔ 块 B 的节点 ↔ head
```

遍历到 `&free_list` 就结束，必须先排除头节点，再使用 `le2page()` 取出页记录。

### Q073：le2page 为什么能从链表节点找到 Page？

**答案：** `page_link` 是嵌在 `struct Page` 内部的成员。知道成员指针后，减去这个成员相对结构体起点的偏移，就得到所属记录：

```text
Page 起始地址 = page_link 的地址 - offsetof(struct Page, page_link)
```

当前 64 位构建中该偏移为 24 字节。宏通过字符指针做字节减法，再转换回 `struct Page *`；不能直接拿 `list_entry_t *` 减 24，否则会按节点大小移动。宏见 [memlayout.h](../kern/mm/memlayout.h)，链表实现见 [list.h](../libs/list.h)。

### Q074：list_init、list_add、list_add_before、list_del 分别做什么？

**答案：** 这些函数只维护节点指针，不理解物理页的含义：

| 操作 | 效果 |
| --- | --- |
| `list_init(node)` | 前后指针指向自身 |
| `list_next(node)` / `list_prev(node)` | 取得后继 / 前驱 |
| `list_add(node, new)` | 把新节点放在指定节点之后 |
| `list_add_before(node, new)` | 把新节点放在指定节点之前 |
| `list_del(node)` | 连接其前后邻居，将节点移出链表 |

本项目的 `list_del()` 不释放 `struct Page`，也不将被移除节点的指针自动清空。页记录一直保留在 `pages[]` 中，“退出空闲链表”和“销毁记录”不是同一个操作。

### Q075：Best Fit 的链表按块大小排序吗，链表相邻是否等于物理相邻？

**答案：** 参考实现按物理地址顺序维护链表，因为同一 `pages[]` 中记录的先后与物理页号一致。分配时遍历比较长度来找最合适的块；释放时利用地址顺序查找相邻块。

链表中的前后节点只说明它们之间没有其他空闲块，可能仍隔着已分配页。只有满足 `left + left->property == right`，两个块才在物理上紧接，能够合并。

### Q076：pmm_manager 是什么，为什么调用它就能换分配算法？

**答案：** 它是包含名称和函数指针的 C 结构体，相当于一张统一操作表。公共包装函数通过当前选择的表调用具体实现：

| 接口 | 含义 |
| --- | --- |
| `init` | 建立管理器的空状态 |
| `init_memmap` | 登记初始可分配物理页 |
| `alloc_pages` | 申请连续页 |
| `free_pages` | 归还页范围 |
| `nr_free_pages` | 查询空闲总页数 |
| `check` | 执行该管理器的自检 |

例如 `alloc_pages(n)` 最终调用 `pmm_manager->alloc_pages(n)`。调用者使用共同接口，而算法由所选函数指针决定。定义见 [pmm.h](../kern/mm/pmm.h)。

### Q077：First Fit 和 Best Fit 都有 free_area，会混用同一份状态吗？

**答案：** 不会。各源文件中的 `static free_area_t free_area` 具有文件作用域，属于各自的管理器。当前选择哪个管理器，就初始化并使用哪个管理器的链表和计数。

选择应发生在登记物理页之前。若运行中仅更换 `pmm_manager` 指针，新管理器不会自动继承已有空闲块和分配状态，不能把这种切换当作完整的算法热切换。

### Q078：如何确认当前运行的是 First Fit 还是 Best Fit？

**答案：** 同时核对源码选择和运行输出。在 [pmm.c](../kern/mm/pmm.c) 的 `init_pmm_manager()` 中，个人分支选择 `&default_pmm_manager`；启动输出相应为 `memory management: default_pmm_manager`。完整参考版本选择 `&best_fit_pmm_manager`，名称也随之变化。

目录里存在 `best_fit_pmm.c` 或编译出了其目标文件，不能单独说明实际调用了 Best Fit。

### Q079：property 和 PageProperty 各自表示什么，为什么只设置块头？

**答案：** `property` 是连续空闲块的页数，`PageProperty` 是“这条记录是有效空闲块头”的标志。只有链表中的块头同时带有有效长度与该标志，其余记录不独立表示块。

例如连续 3 页空闲：`pages[i]` 作为块头，标志为真、长度为 3；`pages[i+1]` 和 `pages[i+2]` 不作为独立节点。因此 `!PageProperty(page)` 不能证明该页已分配，它也可能是空闲块的内部页。是否空闲需结合整个块结构判断，`ref == 0` 同样不足以判断。

### Q080：分配器正常运行时应始终满足哪些条件？

**答案：** 这些条件连接了链表、页状态和计数，也是解释代码与测试的依据：

1. 每个空闲块长度大于零，块头具有 `PageProperty`。
2. 链表按地址递增，块之间不重叠。
3. 能相邻合并的空闲块已经合并，不保留两个紧接的块。
4. 块头长度之和等于 `nr_free`，这里统计页数而非块数。
5. 已分配范围不再属于任何空闲块，保留页也不进入分配器。

这些性质依赖合法的申请、释放调用。当前实现不是能自动修复任意错误输入的通用内存检查器。

## 八、Best Fit 申请与拆分

### Q081：alloc_pages(n) 承诺返回什么，连续具体指什么？

**答案：** 成功时返回首个物理页对应的 `struct Page *`，代表从该页开始的连续 `n` 张物理页；失败返回 `NULL`。连续是物理页号连续，因此物理区间长度为 `n × 4096`。

它不直接返回数据区的 C 指针，也不保证页内数据已经清零。调用者需要记录自己持有的范围和长度，必要时再按映射关系访问实际内存。

以下问题解释完整参考快照 `346331b` 中的算法；可对照已提取的 [Best Fit 参考源码](../../../lab2/交付材料/参考阅读/best_fit_pmm.c)。个人分支中的 Best Fit 尚是待接续骨架。

### Q082：Best Fit 怎样选块，那个 if 条件为什么这样写？

**答案：** 遍历所有空闲块，先要求长度足够，再在足够的块中选长度最小者：

```c
if (page->property >= n &&
    (best == NULL || page->property < best->property)) {
    best = page;
    if (page->property == n) {
        break;
    }
}
```

`page->property >= n` 排除太小的块；`best == NULL` 接受第一个候选；随后只用更小的合格块替换。C 的 `||` 短路求值保证 `best` 为空时不会访问 `best->property`。一旦长度正好为 `n`，已经不存在更小的合格长度，可以提前停止。

### Q083：总空闲页足够，为什么还可能申请失败？

**答案：** 申请要求连续。若空闲块分别为 2 页和 2 页，总数虽为 4，但申请 3 页仍无法满足。这叫外部碎片：空闲总量足够，却缺少所需连续区间。

因此有两次失败判断：`n > nr_free` 可以在遍历前拒绝总量不足；遍历结束后 `best == NULL` 则表示没有任何单块足够大。只做第一项检查会漏掉碎片情况。

### Q084：给定 8 页、3 页、5 页三个块，申请 2 页怎样选择？

**答案：** 假设 A、B、C 依次按地址排列，长度分别为 8、3、5。Best Fit 先暂选 A，再用 B 替换，因为 3 比 8 更小且仍容得下 2；C 长度为 5，不再替换 B。

最终从 B 的开头取 2 页，留下 1 页：

```text
原来：A(8) → B(3) → C(5)，空闲总数 16
结果：A(8) → B 的余块(1) → C(5)，空闲总数 14
```

First Fit 会在发现 A 足够时立即选 A。这是两种算法选择规则的区别，而不是链表排序方式不同。

### Q085：两个块一样大时选哪个，为什么不是用小于等于？

**答案：** 当前参考实现只在新候选严格更小时替换 `best`。链表按地址递增，所以同样合适的块中保留先遇到的，也就是地址较低的块。改成 `<=` 会在同长候选之间继续替换，可能选到更高地址；它会改变本实现的确定性规则。

精确匹配时可以立即退出，因为不可能找到长度小于请求、又满足请求的块。若已有多个精确匹配，也会保留首次遇到的那个。

### Q086：找到 best 后为什么先保存前驱，再把 best 摘掉？

**答案：** 保存 `prev = list_prev(&best->page_link)`，是为了稍后将拆分余块插回原来的位置。取走的块头不再属于空闲块，因此需要 `list_del()`。

这个过程改变的是管理信息，没有复制或搬动物理页中的数据。若要拆分，余块起点仍位于原块内部，保留原链表位置即可继续满足地址有序。

### Q087：拆分为什么是 rest = best + n，余块怎样回到链表？

**答案：** 从块首取走前 `n` 页，余块首记录自然为 `best + n`。长度用原块长减去请求数，再给余块设置空闲块头标志：

```c
struct Page *rest = best + n;
rest->property = best->property - n;
SetPageProperty(rest);
list_add(prev, &rest->page_link);
```

`list_add` 插在原前驱之后。原来的后继位于整个旧块之后，余块仍在原范围内，所以地址顺序不变。正好分配整块时没有余块，不执行此分支。

### Q088：为什么 nr_free 只减 n，不减原块长度？

**答案：** 原块的余下部分仍然空闲，只是更换了块头，所以真正减少的空闲量只有 `n`。选中块头随后清除 `PageProperty`，并将旧 `property` 置零，避免已分配页继续看起来像空闲块头。

本实现不会在这里自动增加引用计数，也不会把分配到的物理页数据清零。块长、引用计数和数据内容应分别理解。

### Q089：申请 0 页、申请超过总数、没有合适连续块，分别怎样处理？

**答案：** 三种情况分别为：

| 情况 | 当前参考实现的处理 |
| --- | --- |
| `n == 0` | `assert(n > 0)` 失败，属于接口使用错误 |
| `n > nr_free` | 直接返回 `NULL` |
| 总数够，但没有单块长度至少为 `n` | 遍历后返回 `NULL` |

后两种失败不会摘链、拆分或减少计数；分配结构应保持原状。申请失败后直接使用空指针属于调用者错误。

### Q090：Best Fit 的复杂度是多少，它一定比 First Fit 更好吗？

**答案：** 设空闲块数为 `k`，Best Fit 一般需要遍历整个链表，时间复杂度为 `O(k)`；遇到精确匹配可提前结束。First Fit 最坏也是 `O(k)`，但找到第一个足够的块就停止，访问块数可能更少。

Best Fit 的目标是减小本次分配后的余块，不保证整个程序未来的碎片最少。它可能留下很多很小的空闲块，实际表现取决于请求序列。不能仅凭“最优适应”这个名字宣称全局最优。

## 九、登记、释放与合并

### Q091：free_pages(base, n) 的调用者必须保证什么，能释放原申请的一部分吗？

**答案：** 必须保证这 `n` 页确实由调用者持有、尚未归还、不含保留页，范围和长度合法，并且后续不再通过旧持有关系使用已释放的页。

本实验允许释放持有范围的一部分；原测试就会先申请 5 页，再释放其中第 1～2 页和第 4 页。因此不能说释放必须永远与某次申请的完整长度完全一致。关键是释放范围当前合法且不重叠，调用者正确维护剩余持有范围。

### Q092：释放函数为什么先遍历每页清状态，再插入空闲块？

**答案：** 遍历阶段检查基本前提，清除该范围的旧标志、长度和引用计数，避免旧管理状态残留。随后统一的插入函数把整段标记为一个空闲块，再与已有邻居尝试合并。

这一步并没有清空物理页的数据。设置 `page->flags = 0` 写的是 `struct Page` 记录中的字段。

### Q093：init_memmap 和 free_pages 有什么区别，为什么可以共用插入函数？

**答案：** 两者进入分配器之前的状态不同。初始化登记要求这些页原先具有 `PageReserved`，表示从保留状态首次开放；普通释放要求页不是保留页，也不是已有空闲块头，表示归还已持有的范围。

完成各自的检查与状态整理后，两者都需要执行“登记一段空闲区、按地址插入、与邻居合并”，因此共用 `best_fit_insert_block()`。共用的是后半段动作，前置条件仍各自保留。

### Q094：插入辅助函数为什么在开头给 nr_free 加 n，而且只加一次？

**答案：** 这次新加入的可分配容量恰好是 `n` 页，所以设置新块头长度与标志后执行 `nr_free += n`。合并只改变表示方式：原来多个块变成一个块，物理空闲页的总量没有增加。

例如原有左右块共 6 页，新归还 3 页，总数应增加到 9；不能在合并时再把左右块的页数重复累加。

### Q095：新块应该插到链表哪里，为什么使用 list_add_before？

**答案：** 从头寻找第一个地址不小于 `base` 的块，将新块插在它之前；若遍历到哨兵头，则插到尾部。

```c
list_entry_t *next = list_next(&free_list);
while (next != &free_list && le2page(next, page_link) < base) {
    next = list_next(next);
}
list_add_before(next, &base->page_link);
```

在输入范围不与现有空闲区重叠的前提下，这能保持按地址递增。这里只确定顺序，不表示函数已完成所有重叠、越界和重复释放验证。

### Q096：与左侧合并的条件和动作是什么？

**答案：** 先确认前驱不是哨兵头，再判断前驱块结束处是否正好等于当前起点：

```text
left + left->property == base
```

成立时，将当前长度加到左块，左块仍是合并后的头；清除旧 `base` 的块头标志和长度，将其移出链表，最后令 `base = left`。指针更新很重要，因为后续向右合并应从这个扩展后的块继续计算。

### Q097：左合并之后，为什么必须重新取得右侧邻居？

**答案：** 左合并已经改变 `base` 指向的块和该块的长度，也移除了旧块头节点。应当从新 `base` 重新读取后继，再判断：

```text
base + base->property == right
```

若相邻，将右块长度加进来，清除右块的块头标志和长度，移除右块节点。最终只留下合并范围最左端的一个块头。

### Q098：没有邻居、只接左侧、只接右侧、两侧都接，结果各是什么？

**答案：** 四种情况都使用同一套“插入 → 尝试左合并 → 尝试右合并”处理：

| 相邻情况 | 最终块头 | 最终长度 |
| --- | --- | --- |
| 两侧均不相邻 | 新归还块头 | `n` |
| 仅左侧相邻 | 原左块头 | `left_size + n` |
| 仅右侧相邻 | 新归还块头 | `n + right_size` |
| 两侧均相邻 | 原左块头 | `left_size + n + right_size` |

例如左边 `[1000,1002)` 有 2 页，新归还 `[1002,1005)` 有 3 页，右边 `[1005,1009)` 有 4 页，最终得到 `[1000,1009)` 共 9 页。这里是 `pages[]` 下标区间，不是字节地址；计数只因新归还而增加 3。

### Q099：为什么只检查左右邻居，不需要再次扫描所有块来合并？

**答案：** 前提是链表已经按地址排序、原来不重叠且相邻空闲块已合并，新归还范围也合法。这样新块能直接接上的已有空闲区只可能是左右邻居。

原来的左块不可能还紧接另一个未合并的左块，否则原状态就违反了条件；右侧同理。因此插入位置确定后，各检查一次足够。如果允许非法重叠输入或原状态已损坏，这个推理不再成立。

### Q100：这些断言能检测所有重复释放吗，释放后页表和数据会消失吗？

**答案：** 不能。`!PageReserved` 和 `!PageProperty` 能发现部分错误，但空闲块内部页本来就可能没有块头标志，因此不能完整识别所有重复释放或重叠范围。参考实现依赖调用者正确管理所有权，也没有在这些函数里实现并发同步。

释放只更新物理页管理信息，不自动清除物理数据，也不自动撤销原有虚拟映射。上层必须保证不再使用已归还内存，不能把“还在映射、还能读到旧值”当作仍有所有权的证据。

## 十、测试与结果解释

### Q101：个人分支的两次启动验证分别说明了什么？

**答案：** [128 MiB 日志](logs/hews-qemu-128m.log) 显示 32768 条记录、31929 个空闲页；[64 MiB 日志](logs/hews-qemu-64m.log) 显示 16384 条记录、15705 个空闲页。两次都选择 `default_pmm_manager`，并输出 `check_alloc_page() succeeded!`。

它们共同支持：启动能够进入 C 代码，初始化随 DTB 内存大小重新计算，可用区能被已有 First Fit 正常登记和用于自检。这两次结果没有验证 Best Fit 的选择规则，因为当时运行的管理器就是 First Fit。

### Q102：basic_check() 检查了什么，为什么暂时保存并清空链表？

**答案：** 它先申请三张不同的页，检查引用计数初值和物理地址范围，再临时保存原空闲链表与计数，建立隔离的小测试环境。空表时申请应失败，归还三页后应能重新申请三次，耗尽后再次失败；单页归还后再申请，应得到那一页。

这样可以在不让原来大量空闲页干扰结果的情况下检查边界。结束时恢复原空闲状态并归还测试页，不能让自检本身长期消耗容量。它是对申请、释放和计数的一组具体检查，不是所有输入的证明。

### Q103：best_fit_check() 怎样区分 First Fit 和 Best Fit？

**答案：** 它先申请连续 5 页，再在隔离环境中释放其中两段：第 1～2 页和第 4 页。用 `*` 表示仍被持有、`-` 表示空闲：

```text
位置：0 1 2 3 4
状态：* - - * -
空闲块：低地址 2 页，高地址 1 页
```

申请 4 页必须失败；申请 1 页时，Best Fit 应选择高地址的 1 页块，即 `p0 + 4`，因为它精确匹配，而不是选择先遇到的 2 页块。随后申请 2 页应成功。最后归还、重组并检查总量恢复。

原始 `basic_check()` 与 `best_fit_check()` 保持不变，额外测试独立补充，不能通过修改原检查来制造通过结果。

### Q104：make test 的 6/6 是什么，为什么之前要 make clean？

**答案：** 测试构建使用 `ucore_test` 宏，使管理器检查中的阶段计分输出生效。`6/6` 表示代码中设定的六个检查阶段走到了通过位置。编译选项变化不一定使旧目标文件自动重编，先清理再构建，可以避免复用普通构建产物而漏掉计分输出。

本骨架中的六阶段计分来自 `best_fit_check()`；First Fit 的 `default_check()` 没有对应分数输出。当前 SLUB 分支运行 `make test` 可以完成页自检和对象自检，但不会因此获得 Best Fit 的 `6/6`，仍须核对管理器名称及具体成功标记。

### Q105：make grade 的 20/20 实际检验了哪些内容？

**答案：** [Makefile](../Makefile) 先清理构建产物，再复制源码到临时目录；[inject.py](../tools/inject.py) 在临时副本中加入测试调用；[grade.sh](../tools/grade.sh) 按两项 PASS 输出分别计 10 分：

| 检查 | 核心内容 |
| --- | --- |
| `test_page_init()` | 偏移、DTB 内存范围、页号上界、数组位置与对齐、空闲总量、内核尾页和数组起点页保留、转换往返 |
| `test_best_fit()` | 当前管理器指针是否为 `&best_fit_pmm_manager` |

第二项本身不遍历验证 Best Fit 算法。`20/20` 应与内核原自检、独立回归共同解释，不能说它已经穷尽拆分、合并和所有碎片情况。测试原文见 [test_lab2.c](../tools/test_lab2.c)。

### Q106：为什么还需要主机回归，是否重新写了一份分配器来代替内核代码？

**答案：** 主机回归直接编译完整参考版本的真实 `best_fit_pmm.c`，补上它在主机环境所需的输出、断言和公共接口包装。它没有用另一份算法替代被测实现。

另一侧用独立的逐页占用表计算预期结果，再与真实分配器比较。这样可以在较多申请与释放组合下检查位置和计数，并使用主机的内存错误检测工具；启动和硬件地址转换仍由 QEMU 测试负责。

### Q107：主机测试的 256 页是什么，occupied 是真正的位图吗？

**答案：** 主机测试建立 256 条 `struct Page` 记录，模拟一个有 256 页的管理范围，并不真的分配 256 张硬件物理页，也不运行 Sv39。

`unsigned char occupied[256]` 中每个字节保存一页的占用状态，0 为空闲、1 为已占用。它在逻辑上扮演逐页状态图，但存储上不是多个状态压在同一字节中的位压缩位图。主机测试将 `nbase` 设为 0，不能把其中页号直接套成 QEMU 的实际物理地址。

### Q108：10,000 次操作怎样产生，释放时会不会随便选一段非法地址？

**答案：** 伪随机状态从固定种子 `0x4c414232` 开始，产生可复现的 10,000 次操作。申请长度在 1～16 页之间；释放时从已成功申请且仍存活的范围表中选取，归还对应的合法范围。

固定种子便于失败后复现同一序列。它覆盖的是这条序列产生的合法使用组合，不表示测试过所有种子、所有尺寸，也不表示故意构造了任意非法释放。

### Q109：每次随机操作后，独立模型怎样判断分配器是否正确？

**答案：** 申请前扫描 `occupied[]`，找出所有连续的空闲段，在长度足够的段中选最小者；同长时保留先遇到的低地址段。真实分配器的结果必须与这个预期起点完全一致，找不到时必须同样返回 `NULL`。

成功后逐页确认原先没有占用，再将对应状态置为已占用；合法释放后清除对应状态。每次还统计模型中的空闲页数，要求它与 `nr_free_pages()` 一致。因此检查的不只是“没崩溃”，还包括选择位置、避免重复分配和总量正确。

### Q110：如何验证初始化区间乱序到达也能合并，以及最终没有丢页？

**答案：** 主机测试先登记后半段 128 页，再登记前半段 128 页，然后要求能一次申请全部 256 页。这验证了按地址插入和初始相邻区间合并，而不依赖登记顺序恰好递增。

随机回归结束后，再归还所有存活申请，要求总空闲数恢复为 256，并能从 `pages` 起一次申请完整 256 页。这个末尾检查同时约束了容量恢复和连续块恢复。

### Q111：ASan 和 UBSan 各自提供什么证据？

**答案：** AddressSanitizer 帮助发现这次主机运行中可检测到的越界、非法内存访问等问题；UndefinedBehaviorSanitizer 帮助发现已启用检查所覆盖的未定义行为，例如部分错误的运算与访问。

没有报告错误，表示这次执行中未发现相应问题。它们不会自动证明算法策略正确，也不能替代 DTB、启动页表和 QEMU 验证。逻辑正确性由预期模型与断言共同检查，有限测试仍不是形式化证明。

### Q112：QEMU 被 timeout 结束，退出码 124 是否表示实验失败？

**答案：** 124 表示外部 `timeout` 到时终止命令。内核完成初始化和自检后进入无限循环，正常情况下也会被超时工具结束。

必须结合输出判断：已经出现正确管理器、内存布局与 `check_alloc_page() succeeded!`，可以说明走到了成功位置；若只有固件输出或出现 panic，则相同退出码不能解释为通过。退出码不能替代成功标记。

## 十三、SLUB 扩展、回归与结果

### Q127：Best Fit、Buddy 和 SLUB 分别位于哪一层？

**答案：** Best Fit 与 Buddy 可以实现底层物理页管理，向上提供连续页面；SLUB 是其上的对象分配层，将页面用于不同长度的内核对象。当前 SLUB 使用公共 `alloc_pages()/free_pages()`，底层实际仍为 First Fit。SLUB 不要求先完成 Buddy，也不会自动替换 `pmm_manager`。

### Q128：已经有页分配器，为什么还需要 SLUB？

**答案：** 每个小对象都独占 4096 字节页会浪费空间。SLUB 从底层取得页面，在一页中布置多个同规格槽位。例如当前 128 字节缓存每页可放 31 个对象，几十字节的请求不必每次独占一页。规格向上取整仍有内部碎片，但多个小对象可以共享页面。

### Q129：alloc_pages 返回的 Page 指针与 kmalloc 返回的指针有何区别？

**答案：** 前者指向页管理数组中的记录；通过 `page2pa()` 获得被描述的物理页位置，再加当前映射偏移才访问数据页。`kmalloc()` 返回 `void *`，直接指向对象内容。SLUB 内部完成“页记录 → 物理地址 → 内核虚拟地址 → 页内对象”的转换，调用者只读写对象并用 `kfree()` 归还。

### Q130：对象规格怎样选择，申请 40 字节会发生什么？

**答案：** 缓存规格为 16、32、64、128、256、512、1024、2048 字节。选择不小于请求的最小规格，所以 40 字节进入 64 字节缓存。已有 partial slab 时弹出其空闲对象；没有时先申请一页，初始化槽位再返回。成功保证至少请求长度可写，不要求调用者先自己取整。

### Q131：什么叫 slab，它的元数据放在哪里？

**答案：** slab 是承载一批同规格对象的内存区域。本实现每个小对象 slab 用一页，开头放管理结构，后面是槽位。当前结构体 120 字节，对齐后对象区从偏移 128 开始，因此 16 字节槽位有 `floor((4096-128)/16)=248` 个。元数据随底层页面一起取得，不依赖先调用对象分配器。

### Q132：对象 freelist 为什么可以占用对象本身的内容？

**答案：** 空闲对象还没有交给调用者，可以把开头的一个指针用于连接下一空闲对象。申请时先读出下一项并弹出当前对象，随后这些字节归调用者写入；归还时再把链指针写回。该链表节点代表槽位，缓存的 partial 链表节点代表整张 slab，两者不要混淆。

### Q133：partial、full、empty 的状态变化是什么？

**答案：** partial 表示还有空闲槽位；填满后移出 partial，成为 full；full 归还一个槽后重新进入 partial。使用数量变为零时是 empty，本实现立即移出管理链并归还整页。容量为 1 的 slab 释放唯一对象时，也会完成相应脱链再归还，不长期保留空 slab。

### Q134：kfree 不接收长度，怎样知道要归还什么？

**答案：** 每个返回指针位于所属跨度的第一页，向下按页对齐后，在已有登记链中查找该跨度。头部记录它是哪个缓存的 slab，或是直接申请的多页对象。小对象通过偏移和规格求槽位下标，大对象检查精确返回位置并读取记录页数。因此调用者不需要再次传长度。

### Q135：6000 字节和 4096 字节怎样分配，为什么有时需要额外一页？

**答案：** 大于 2048 的请求直接申请容纳头部加数据的连续页。当前头部偏移为 128：6000 字节需要 `ceil(6128/4096)=2` 页；4096 字节需要 `ceil(4224/4096)=2` 页。2049 字节走大对象路径但一页就够。额外成本来自元数据；需要原始整页的模块可以直接用页接口。

### Q136：返回地址对齐到多少，是否保证清零？

**答案：** 至少 16 字节对齐，因为页起点、头部偏移及各槽位间距均满足这一条件。没有承诺每个对象按其整个规格对齐，也没有保证返回内容为零。调用者需要初始化自己的数据；这与 Linux 的全部 `kmalloc` 语义不完全相同。

### Q137：零长度、NULL、溢出和极大请求分别怎样处理？

**答案：** `kmalloc(0)` 返回 NULL，`kfree(NULL)` 无动作。大对象先检查加头部是否超过 `size_t` 上限，再按整除加非零余数计算页数，避免向上取整自身再次溢出。加法不溢出但总容量不够的请求，也由底层失败并返回 NULL；失败不应登记半完成对象或消耗页面。

### Q138：物理页耗尽后，为什么仍可能申请到小对象？

**答案：** 页面已经归某张 slab 持有时，其中未使用的槽位不再算作底层空闲页，但仍是对象层可用空间。相应缓存有空槽就可以继续申请；只有创建新 slab 或直接取得大对象页面才需要底层空闲页。耗尽测试专门区分了这两种情况，并检查原对象内容不变。

### Q139：为什么最后一个对象释放后就归还 slab，有什么取舍？

**答案：** 立即归还能让其他缓存或页级调用者复用内存，也便于验证所有对象释放后物理页数恢复。代价是下一次同类申请可能再次向底层取页并重建对象链。保留若干空 slab 可减少反复创建，但要增加缓存上限和回收策略；当前为简化实现选择即时归还。

### Q140：SLUB 占用位图与 Page 的 flags 是同一份状态吗？

**答案：** 不是。SLUB 位图每一位描述该 slab 中一个对象槽位是否已分配，用于对象层管理；`Page.flags` 描述物理页记录的保留或空闲块头状态。整个 slab 页在底层看来已分配，即使里面还有许多空槽。本实现没有借用或修改 `struct Page` 的布局来保存对象元数据。

### Q141：哪些测试能说明小对象没有互相覆盖，而且释放后真的能复用？

**答案：** 29 种边界尺寸同时申请，逐对比较存活区间，并写满各自请求长度、用不同模式核对内容。复用测试填满两个 slab 并撤销第三张新页，使已有 slab 只有一个刚归还的空槽；再次申请必须得到它且不减少空闲页。全部交错释放后要求页总量恢复。这比只检查返回值非空更能约束实现。

### Q142：随机回归做了多少次，怎样保证测试本身独立？

**答案：** 内核自检执行 2000 次，种子为 `0x4c414232`；主机另执行 20000 次，种子为 `0x534c5542`。测试自己维护存活对象、请求长度与数据标签，不读取私有 slab 布局，检查新范围不与任何存活范围重叠，并在释放、周期检查和结束时验证数据。固定序列便于重现，但不是所有可能操作的证明。

### Q143：七类非法释放具体是什么，能解决所有悬空指针问题吗？

**答案：** 包括陌生指针、小对象内部指针、大对象第一页内部指针、大对象后续页指针，以及 slab 仍存活、slab 已清空、大对象已归还三种重复释放。主机分别启动独立进程，要求在对应检查处 panic，不能以地址检测器崩溃算通过。

它不能辨认地址已经重新分配后的旧指针身份，也没有自动阻止所有越界写。调用者仍须遵守所有权和长度约定。

### Q144：为什么做 SLUB 却修改了 default_pmm.c？

**答案：** 扩展测试暴露出底层已有缺陷：两个尾插分支插入后没有停止遍历。尾节点的 next 已变为新节点，继续循环会处理这个新节点并把它插到自身之后，破坏链表。主机第 32 步发现对象重叠，QEMU 在耗尽回收阶段未完成。分别补一个 `break` 后，同一场景通过；原自检函数没有改动。

### Q145：只看到空闲页总数恢复，为什么还不够？

**答案：** 计数变量可能正确而链表已经损坏，导致重复分配或连续区丢失。本次初轮失败就出现过这种情况。因此主机除检查恢复 256 页，还要求能从起点一次申请完整 256 页；随机测试另查重叠与数据。容量、连续性和存活对象完整性应共同核对。

### Q146：ASan/UBSan 是否知道模拟 RAM 里每个对象的边界？

**答案：** 不会自动知道。模拟 RAM 是一整块主机数组，自定义槽位不是每次都由 libc 单独申请；数组内部跨对象写入可能仍处于 sanitizer 认为可访问的范围。所以 sanitizer 提供运行期地址和未定义行为检查，独立区间、模式数据、计数与复用检查共同补充对象层逻辑验证。

### Q147：现场怎样演示 SLUB 扩展？

**答案：** 在仓库根目录加载环境后运行：

```bash
source ../Lab1前置准备/activate.sh
make -C lab2 clean
make -C lab2
timeout 15s make -C lab2 qemu
make -C lab2 slub-host-test
```

QEMU 同时应有 `check_alloc_page() succeeded!` 与 `slub_check() succeeded!`，主机应有 `Host SLUB ASan/UBSan: PASS`。两份设计提示词、尺寸覆盖、64 MiB 命令及真实日志见 [slub.md](slub.md)。外部超时 124 与成功标记分别解释，当前 First Fit 不宣称 Best Fit 的 `20/20`。

### Q148：SLUB 新构建的地址和能力范围，怎样与旧文档区分？

**答案：** 当前增加了代码及测试数据，`end=0xffffffffc0208e0c`，页记录起点的物理地址为 `0x80209000`，默认空闲起点为 `0x80349000`、31927 页；64 MiB 时为 `0x802a9000`、15703 页。启动根表物理地址为 `0x80206000`，对应 satp 示例值 `0x8000000000080206`。旧阶段的 `0x80207000`、31929 等数字应与其旧日志一起理解，公式没有变化。

当前实现保证无并发调用场景的对象分配，保留大小缓存、freelist、partial 与空 slab 回收思想，省略 Linux 的 per-CPU、NUMA、并发同步等机制。主机与两种内存配置的验证证明已执行场景，没有代替未集成的 Buddy 或整个课程交付。
